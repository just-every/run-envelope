# Worker privacy and local retention

The native privacy API is under the company and person routes:

- `GET /api/envelope/companies/{company}/people/{person}/privacy` returns the structured retained set, field names, record keys, content-bound fingerprint, legal basis, custodian and earliest UTC release gate. It returns no private field values. Only the configured native owner with a current company owner grant can read it; every successful inventory read is audited.
- `POST` to the same path ending in `/retain` records an explicit legal classification. Supply the current `fingerprint`, an exact array of selected `records` IDs, `legalBasis`, `custodian`, `earliestReleaseAt` and `consent: true`. The instant must use UTC with milliseconds. Unclassified dependencies default to statutory retention with no releasable gate. An established gate can be extended but cannot be shortened through reclassification.
- `POST` ending in `/release` requires the same current fingerprint, exact record selection, an explicit release basis and consent. A fresh native sensitive-action proof is required. Each selected record must already have a classified, elapsed gate; the release is attributed and audited. Time alone never releases a hold. Changed record contents require a new review and release.
- `POST /api/envelope/companies/{company}/people/{person}/erase` requires the current person `version`, `consent: true`, fresh native sensitive-action proof and, for dependent records, the reviewed `fingerprint` and the exact array of all dependent `records` IDs. Every dependency must have an explicit current release. A released record remains present until this separate destructive gesture.

The same privacy routes are available as native forms from the worker screen's **Privacy and retention** link. The retained record families expand by keyboard or pointer to show every selected key, field, custodian, legal basis and UTC gate.

- `POST /api/envelope/companies/{company}/people/{person}/privacy/request` persists a held request. Supply the current `fingerprint` and explicit `consent: true`; fresh native proof is required. Repeating the request does not duplicate it.
- `GET /api/envelope/companies/{company}/privacy-requests` returns owner-only audited request history. The native page uses the same path beneath the app prefix. A completed request keeps an opaque receipt, timestamps and deletion count, with no worker identifier. A refused review remains held and the native form explains that no action completed.

While an explicit request is held, company reads and use are paused for other identities, including sponsored agents and previously issued protected responses. The configured native owner retains audited custody. This conservative company fence protects shared payroll derivatives; grants are not silently removed or expanded. A release does not reopen these transports before the separate erasure completes.

The local inventory follows company-scoped person references, SQL relationships, encrypted workspace references, derivative source pins and mapped hire sources. An owner can explicitly associate a worker-bearing notice through `POST /api/envelope/companies/{company}/notices/{notice}/people`, supplying `personId`, the exact notice `digest` and `consent: true` after fresh native proof. Each worker has a distinct immutable association with the same notice. Either worker inventory includes both associations and the notice body, analysis, all reply versions, review challenges, approvals, dispatch references and retained case originals in the worker inventory. A notice is never assigned by searching for a name in its text. Retired notice references cannot be imported again under a fresh random identifier. All versions of a selected workspace object join the inventory, including an initial claim request recorded before a native worker was attached. Firm work follows its source reference; embedded claim originals disappear with their owning encrypted versions. Deletion, journal tombstones, source replay fences and action-target anonymization commit together. The permanent audit removes erased worker attribution while keeping independent administrative actors and shared native identities intact. Agent action targets are anonymized too; a denied read cannot recreate an erased claim target in the audit. A concurrent product edit, changed authority, failed constraint or still-held record rolls the transaction back. Existing export snapshots are invalidated. A redaction checkpoint prevents an older archive from restoring the previous action targets when a later journal is supplied. Source IDs retired by erasure cannot be reused through the workspace intake door; mapped hire identities are also fenced.

There is no automatic payroll erasure, hold release or external destructive request. Downloaded copies and already-filed agency records are outside local recall. External provider deletion is a separate authorized obligation and this API sends no request.

ENV-054 remains partial. The archive journey covers the native record families below, but it does not certify every present and future custody transport or an external provider's deletion. The recorded continuation matrix includes reporting sources, responses and transfer authority, withholding originals, shared notice associations and the current shared run-intake door. These local assertions establish no official external deletion request, authentic provider receipt or independently supported external completion. Future transports inherit the same custody duty.

## Separate provider follow-up

`GET /api/envelope/companies/{company}/privacy-provider-requests` returns the configured native owner's encrypted, attributed request history. `POST` to that route creates a request with `version: 0`, `consent: true`, an existing local privacy `requestId`, a declared `provider`, a minimal opaque `reference`, `status: requested` and redacted `evidence`. Supply no worker names, identifiers, payroll facts or credentials in reference or evidence text.

`POST` to the same route ending in `/{request}` appends an exact expected `version`, consent, evidence and the next status. Every mutation needs fresh native proof. The allowed transitions are:

- Requested to submitted.
- Submitted to unknown, rejected or confirmation-reported.
- Unknown to rejected or confirmation-reported.
- Rejected to submitted after separate human follow-up.
- Confirmation-reported is terminal; replay and stale versions refuse.

Provider, local request and original reference remain immutable. History records the native actor, time and version. Cross-company request binding, ordinary staff, signed-out and agent access refuse. The log is separate from the erased worker graph: local completion preserves an unresolved provider request and never changes its outcome. The fixture proves this separation and the ordered history through the native route.

Every entry is labeled `owner-attested` and `externalDeletionVerified: false`, including a reported confirmation. No request is sent, no provider credential is used and no external destruction is performed by this log. Provider receipt authenticity, the official request and response edge, provider retention obligations and independently supported completion remain unproved. Downloaded copies and already-filed agency records remain outside local recall.

The adopted conservative default performs no external destructive action. A provider-specific deletion transport needs ct approval, explicit authority, exact retained-artifact scope and an appropriate official request channel. Until those are established, the separate owner-attested log remains the conservative default, and ENV-054 remains PARTIAL. No official deletion receipt is claimed.
